In an untrusted repository toolr reads only what it needs to find the repository and its trust
record: it checks that `tools/pyproject.toml` exists, without opening it, and reads git's `.git` and
worktree back-link files. It neither reads nor writes `tools/.toolr-manifest.json`, parses nothing
under `tools/` and doesn't look inside `tools/.venv`, so inspecting an unfamiliar checkout leaves it
untouched. `toolr project venv path` now asks for trust too. Once you trust a repository, toolr uses
an in-tree `tools/.venv` only if it built that venv itself. toolr never runs any other in-tree venv,
including one an older toolr built or one made with `uv venv`, since it may have come with the
repository. The first time a command needs the venv, plugin commands included, toolr explains why
and asks before it removes the venv and builds a fresh one; until then `--help` leaves out its
plugin commands. Only a `y` on a terminal or `TOOLR_REPLACE_UNTRUSTED_VENV=1` approves the removal,
not `TOOLR_AUTO_SYNC`; with `-q` or no terminal toolr leaves the venv in place and says how to
approve. When toolr can't take the sync lock in its trust store, for example because the store is
read-only, it leaves the venv in place: the sync fails and names the store.
