# Self-contained agent skills: implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use
> superpowers:subagent-driven-development (recommended) or
> superpowers:executing-plans to implement this plan task-by-task. Steps use
> checkbox (`- [ ]`) syntax for tracking.

**Goal:** Each `skills/<name>/` directory works when installed alone, with no
repo checkout and no network. A gate keeps it that way.

**Architecture:** `cargo xtask build-skill-refs` gains three sources:

- code-derived tables, from a catalogue in `toolr-core`;
- named docs sections, pulled out by a small Markdown extractor;
- a verbatim example copy.

A self-containment lint runs on every `build-skill-refs` invocation. Docs
include the same generated tables, so code is the single source for both.

**Tech Stack:** Rust (xtask, toolr-core), mkdocs + pymdown-extensions 11.0.2
snippets, Markdown.

**Spec:** `specs/2026-09-27-skills-self-contained-design.md`

**Branch:** `skills-self-contained` (git-spice). The `packslip` branch stacks on
it. Never commit to `main`.

## Model assignment

| Task | Implementer | Adversarial reviewer |
| --- | --- | --- |
| 1. Type and path catalogues (`toolr-core`) | `sonnet` | `opus` |
| 2. Generated tables into skill + docs | `sonnet` | `opus` |
| 3. Docs section extractor (xtask) | `opus` | `llmtrim-codex` (cross-family) |
| 4. Wire sections + example copy into skills | `sonnet` | `opus` |
| 5. Short facts + cross-skill references by name | `sonnet` | `opus` |
| 6. Self-containment gate | `opus` | `llmtrim-codex` (cross-family) |
| 7. Final verification, release note, archive spec | `sonnet` | whole-branch review: `opus` |

The reasoning:

- The parser-like tasks (3, 6) have the most edge cases. They get the
  strongest implementer and a reviewer from a different model family, so the
  reviewer doesn't share the implementer's blind spots.
- The mechanical tasks get `sonnet` to implement and `opus` to review.

## Global Constraints

- Every generated Markdown file starts with the existing header:
  `<!-- generated by \`cargo xtask build-skill-refs\`; do not edit by hand -->`.
  Generated TOML files start with
  `# generated by \`cargo xtask build-skill-refs\`; do not edit by hand`.
- Generated output must be byte-identical across runs. Add every new generated
  path to `crates/xtask/tests/idempotency.rs`.
- Generated docs snippets are `.md` files under
  `docs/writing-commands/files/`, listed in `mkdocs.yml` `exclude_docs` so
  mkdocs never builds them as orphan pages. `pymdownx.snippets` reads from
  disk, so the includes still work, and rumdl keeps linting them as Markdown.
  Don't use `.txt` for generated Markdown: it hides the file from the
  Markdown linters.
- Run docs builds with `uv run --group docs mkdocs build --strict`. The docs
  dependencies live in the `docs` dependency group.
- Snippet include paths are repo-relative (`base_path: .`). An example is
  `--8<-- "docs/writing-commands/files/x.py"`.
- The real path-constraint keywords are `must_exist`, `must_be_file` and
  `must_be_dir`. The docs spellings `path_must_*` are wrong.
- Never write the employer's name, or absolute `/Users/...` paths, into the
  repo. Run `git grep -i <employer-name>` before committing.
- Never `git add -A`. The untracked `audit/` and `ONBOARDING.md` are local-only.
  Stage by path and check `git diff --cached --name-only`.
- Conventional Commits. No `Co-Authored-By` trailer. No `--no-verify`.
- Python test imports go at the top of the file. Use factory fixtures for
  `tmp_path` setup.
- Comments explain *why*, not *what*. Default to none.

## Review Focus

1. **A snippet include with a line range (`file:20:31`) inside an extracted
   section.** Expected: exactly lines 20–31, 1-based and inclusive, expanded in
   place. Test in Task 3.
2. **A link with an anchor into another docs page (`[x](context.md#run)`)
   inside an extracted section.** Expected: plain text `x` with no dangling
   path. Test in Task 3.
3. **A Markdown link inside a fenced code block**, for example Python that
   contains `[a](b)`. Expected: code blocks pass through byte for byte. No
   link rewriting and no gate violations inside fences. Tests in Tasks 3 and 6.
4. **A skill that mentions the user's own `tools/` or `.github/workflows/`
   paths.** Those are user-project paths, not repo paths. Expected: the gate
   allows them. Test in Task 6.
5. **Regenerating after editing a docs section, then running
   `mkdocs build --strict`.** Expected: the docs still render and the skill
   reference changes. This is covered by the Task 7 full run.

### Task 3: Docs section extractor

**Files:**

- Create: `crates/xtask/src/build_skill_refs/docs_section.rs`
- Modify: `crates/xtask/src/build_skill_refs/mod.rs`, to add
  `mod docs_section;`

**Interfaces:**

- Produces:
    - `pub fn extract(repo_root: &Path, doc_rel: &str, section: &str) -> Result<String>`.
  It reads `repo_root/doc_rel`, finds the named section, and returns
  agent-ready Markdown.
    - The pure core, for tests:
  `fn transform(section_src: &str, resolve_include: &dyn Fn(&str) -> Result<String>) -> Result<String>`.

**Behaviour. Each item gets a unit test.**

1. **Markers.** A section runs from the line that contains
   `--8<-- [start:<name>]` to the line that contains `--8<-- [end:<name>]`.
   Both lines are excluded. Markers may be wrapped in `<!-- … -->`.
   - Error when the start is missing, the end is missing, or the section
     appears twice.
2. **Includes.** A line whose trimmed content is `--8<-- "path"` or
   `--8<-- "path:A:B"` is replaced by the file's contents (lines A..=B,
   1-based, for the range form).
   - The replacement keeps the include line's leading indentation on every
     line.
   - Line-range bounds outside the file are an error.
   - A trailing newline in the included file doesn't produce a blank line.
   - Includes are expanded inside code fences too. That is where the docs use
     them.
3. **Fences.** Everything between an opening line that starts with ` ``` ` or
   `~~~` and the matching close is copied byte for byte, apart from include
   expansion. No other transform runs there.
4. **Links**, outside fences only:
   - `[text](other.md)`, `[text](other.md#x)`, `[text](../x/y.md)` and
     `[text](#anchor)` become `text`.
   - `http(s)://` links are kept.
   - Image links `![alt](path)` that aren't `http(s)` are an error, because
     they can't ship.
5. **Admonitions.** `!!! kind "Title"` or `!!! kind`, followed by
   4-space-indented body lines, becomes
   `> **Kind — Title:** first body line` plus `>` for each remaining body
   line, dedented by 4. With no title, it's `> **Kind:** …`. `kind` gets its
   first letter capitalised.
6. **Attribute lists.** A `{: …}` token or a whole line of one is removed.
7. **Unknown constructs are an error** and name the line number:
   - `???` and `???+` (collapsible details);
   - `=== "` (tabs);
   - any other `--8<--` form;
   - raw `<details`, `<div`.
8. **Output** is trimmed of leading and trailing blank lines and ends with
   exactly one `\n`.

### Task 6: Self-containment gate

**Files:**

- Create: `crates/xtask/src/build_skill_refs/self_contained.rs`
- Modify: `crates/xtask/src/build_skill_refs/mod.rs`. `run` calls the lint

**Interfaces:**

- Produces:
    - `pub fn lint(repo_root: &Path) -> Result<()>`
    - The pure core:
  `fn lint_file(skill_dir: &Path, rel: &Path, body: &str, exists: &dyn Fn(&Path) -> bool) -> Vec<Violation>`
    - `struct Violation { file: PathBuf, line: usize, target: String, rule: &'static str }`

**Rules.** They apply only outside fenced code blocks.

- **Files scanned:** each `skills/*/SKILL.md`, and every file under
  `skills/*/references/` and `skills/*/examples/`. Only `.md` files are
  scanned; other examples are copied verbatim and skipped. `README.md`,
  `REVIEW.md` and `tests/` are never scanned.
- **Rule `link-escapes-skill`:** a Markdown link or image with a non-URL
  target that, joined to the file's directory and normalised lexically,
  isn't inside `skill_dir`, or doesn't exist.
- **Rule `repo-url`:** any link or bare URL whose host and path start with
  one of:
    - `github.com/s0undt3ch/toolr`
    - `github.com/s0undt3ch/ToolR`
    - `raw.githubusercontent.com/s0undt3ch/`
    - `toolr.readthedocs.io`

  Case-insensitive.
- **Rule `repo-path`:** a backticked token that starts with `docs/`,
  `crates/`, `examples/`, `specs/` or `skills/` and doesn't exist relative to
  `skill_dir`.
    - This means a skill's own `examples/…` passes, and the repo's
  `examples/plugin-package/` fails.
    - `tools/`, `.github/` and anything else are user-project paths and are
  allowed.
    - Prose that names `examples/plugin-package/` as background must say it
  without backticks, or name the repository explicitly. Make Task 4's prose
  comply.
- **Output:** the error lists every violation as `<file>:<line>: <rule>: <target>`
  and ends with a hint: "skills must be self-contained; see
  specs/archive/…/skills-self-contained-design.md". Use the post-archive path
