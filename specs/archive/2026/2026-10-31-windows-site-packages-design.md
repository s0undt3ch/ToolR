# One site-packages locator for every venv layout

- **Status:** implemented
- **Origin:** whole-project review finding F-14 (medium).
- **Plan:** [`2026-10-31-windows-site-packages-plan.md`](./2026-10-31-windows-site-packages-plan.md)
- **Follows:** F-07,
  [`specs/archive/2026/2026-10-30-plugin-glob-escape-design.md`](./2026-10-30-plugin-glob-escape-design.md).

## Problem

Three places work out where a venv keeps its `site-packages`, each in its own way:

| Locator | Layouts | How |
|---|---|---|
| `crates/toolr/src/build_manifest_resolve.rs` `find_in_venv` | `lib/python*/site-packages` only | glob |
| `crates/toolr-core/src/venv/validate.rs` `candidate_site_packages` | `Lib/site-packages` on Windows, `lib/python*/site-packages` elsewhere | `cfg!(windows)` + `WalkDir` |
| `crates/toolr-core/src/third_party/glob.rs` `glob_manifests` (via `candidate_layouts`) | both, every platform, case-insensitive | glob |

`find_in_venv` has no `Lib/site-packages` pattern, so on Windows `toolr self build-manifest <package>` always fails:

```text
toolr: package `my_plugin` not found under <repo>\tools\.venv; run `uv sync` or pass --source-dir
```

The package is installed at `<venv>\Lib\site-packages\my_plugin`. The `--source-dir` route works.

The three also disagree on cross-platform venvs. `candidate_site_packages` checks one layout per OS;
`glob_manifests` checks both on purpose (see its `candidate_layouts` comment). Any new layout, such as a
free-threaded `lib/python3.14t/`, has to be handled three times.

F-07 already escapes the venv path in `glob_manifests` and `find_in_venv`, and the package name in `find_in_venv`,
and left this layout gap to this change.

## Decision

One helper in toolr-core lists the `site-packages` directories that exist in a venv, and all three callers use it.

```rust
/// Existing `site-packages` directories in `venv_dir`, sorted: `lib/python*/site-packages` and
/// `Lib/site-packages`, on every platform.
pub fn site_packages_dirs(venv_dir: &Path) -> Result<Vec<PathBuf>, SitePackagesError>
```

It lives in a new `crates/toolr-core/src/venv/layout.rs` and is re-exported as `toolr_core::venv::site_packages_dirs`.
It never lists `venv_dir` itself. It lists `<venv>/lib` and keeps `<venv>/lib/<child>/site-packages` for each child
whose name starts with `python`, then probes `<venv>/Lib/site-packages` and `<venv>/lib/site-packages`. The result
is sorted and deduplicated, and holds only directories that exist.

A missing venv or `lib` gives an empty list. An unreadable `lib`, `Lib/site-packages`, or `site-packages` of the
Python that `pyvenv.cfg` names is a `SitePackagesError` carrying the path and the OS error, so an unreadable venv never
reads as "nothing installed". Any other `python*` directory that can't be read, such as one an older Python left
behind, is skipped. `locate_toolr_package` and `installed_toolr_py_version` return the error too, and
`validate_venv` reports it as `ValidationError::Io`. Those two lookups use `preferred_site_packages_dirs`, which puts
the `pyvenv.cfg` Python first and the rest by descending version.

Listing the directory instead of globbing means there is no pattern, so no escaping. A `[`, `]`, `*` or `?` in the
venv path stays literal, which is what F-07 fixed. F-07's tests (`find_in_venv_under_bracketed_venv`,
`glob_finds_fragments_under_bracketed_venv`, `glob_ignores_sibling_matched_by_bracket_class`,
`glob_finds_fragments_under_star_and_question_venv`, `third_party_hash_sees_fragments_under_bracketed_venv`) stay as
they are and guard against undoing it.

On a case-insensitive file system `Lib/site-packages` and `lib/site-packages` are one directory, kept once under the
`Lib` spelling (compared by device and inode on Unix; Windows file systems always ignore case).

The callers:

- `find_in_venv` keeps the first `sp.join(package)` that is a directory, in `site_packages_dirs` order, and still
  warns when more than one matches. The error becomes `` no site-packages directory in <venv> contains `<package>` ``.
  `glob` is no longer used in `crates/toolr`, so its dependency goes from `crates/toolr/Cargo.toml`.
- `glob_manifests` keeps its name and signature. For each site-packages directory it lists the entries and keeps
  `<entry>/toolr-manifest.json` when it is a file. Sorted and deduplicated as before. `candidate_layouts` and the
  `MatchOptions` go. A `read_dir` failure on an existing site-packages directory maps to the existing
  `ThirdPartyError::Io`. The unused `ThirdPartyError::Pattern` and `ThirdPartyError::Glob` variants go.
- `candidate_site_packages` is removed; `locate_toolr_package` and `installed_toolr_py_version` call
  `site_packages_dirs`. On Windows they now also see a `lib/python*/` layout, and elsewhere a `Lib/` one. That's a
  superset of today's behaviour.

`site-packages` and `toolr-manifest.json` are matched by exact name now; the glob matched them ignoring case. uv
and `venv` always write them in lower case, and a case-insensitive file system still finds them through `join`.

Rejected alternatives:

- **Add a `Lib/site-packages` pattern to `find_in_venv` only.** It fixes the symptom and leaves three locators.
- **Keep globbing in a shared helper that escapes the prefix.** It works, but it keeps F-07's class of bug one
  forgotten `Pattern::escape` away. There are no wildcards left once the layouts are listed.
- **Ask the venv's Python for `sysconfig.get_paths()["purelib"]`.** Exact, but it runs an interpreter during
  manifest freshness checks, which are designed to execute nothing.

## Scope and compatibility

- No manifest or runner schema change. `third_party_hash` is unchanged for uv- and `venv`-created layouts. The hash
  covers each fragment's path, and the old glob spelled the `Lib` part as written in its pattern, while the listing
  uses the on-disk name. They differ only on a case-insensitive file system holding a lower-case `lib/site-packages`
  (the old glob hashed it as `Lib/...`). Neither tool writes that layout, and a changed hash only triggers one
  manifest rebuild.
- Docs: the `glob.rs` module doc says how fragments are found and is quoted into
  `skills/toolr-command-packaging/references/packaging.md`; regenerate with `cargo xtask build-skill-refs`. Fix the
  stale `candidate_site_packages` reference in `crates/toolr/tests/project_venv_run.rs`. `docs/third-party.md` and
  `docs/internals/manifest.md` name `lib/python*/site-packages`; add `Lib/site-packages` on Windows.
- `UNRELEASED.md`:

  > `toolr self build-manifest <package>` now finds the package on Windows, where it lives under
  > `Lib\site-packages` in the tools venv. It used to look only under `lib/python*/site-packages` and always reported
  > the package as not found. toolr now finds `site-packages` in the same way everywhere it looks.
